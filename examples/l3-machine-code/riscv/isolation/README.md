# RISC-V L3 model: PMP isolation of U-mode steps

Theorems about the HOL4 RISC-V model of `../model` (`riscvTheory`, generated by L3 from
`../src/riscv.spec`) and nothing else: every step of the model's step function `Next` taken in
U-mode with address translation off respects the PMP configuration. A step writes only bytes
that the PMP lets U-mode write, fetches only bytes it lets U-mode execute (and is an
instruction access fault otherwise), reads only bytes it lets U-mode read or execute (and the
CLINT), and leaves the M-mode state alone except as a trap entry changes it. The statements are
against `Next` itself, so interrupts, exceptions and every instruction of the model are
covered. `DESIGN.md` has the design, the memory paths of the model and the proof architecture.

`riscv_trapTheory` adds what an M-mode kernel that takes system calls by `ecall` needs to know
of the step that enters it and of the steps that take no interrupt: a U-mode step that runs
ECALL is exactly the trap entry into M-mode, with every other CSR, the GPRs and memory
unchanged, and a U-mode state that takes no interrupt while the timer interrupt is enabled has
none pending. `riscv_pmpTheory` also says where a byte that U-mode may access lies: in the
region of the lowest-numbered entry that matches it, which allows the access, and when every
entry is OFF or NAPOT, in that entry's NAPOT region.

`riscv_refineTheory` relates `Next` to the step library's `NextRISCV` (`../step`), the step
function of the M-mode step theorems with which HolBA lifts programs: from a state that takes
no interrupt and whose fetched instruction reads no counter CSR, a `NextRISCV` step is a `Next`
step up to six ghost fields of the state that `NextRISCV` does not maintain (the log, the
access record `c_update`, the exception, the cycle and instruction counters and the flag that
`minstret` was written), from any state that agrees with it on every other field.
`riscv_trapTheory`, `riscv_refineTheory` and their examples are the only theories here with the
step library's `riscv_stepTheory` as an ancestor.

## Building

    cd examples/l3-machine-code/riscv/isolation
    Holmake

It uses the heap `../step/riscv-heap` and builds `../model` and `../step` first if needed. From
clean, with `../step` built, the nine theories took 6 m 25 s on a machine shared with other
builds (single job: footprint 2 m 08 s, frames 53 s, pmp 9 s, isolation 1 m 22 s, example 4 s,
trap 17 s, trap example 4 s, refine 1 m 06 s, refine example 1 s; on an idle machine the first
five took about 4 m 40 s) and at most 2.1 GB of memory (peak resident size of the build,
reached in footprint; refine took at most 1.3 GB). No `cheat`, axiom or oracle is used: every
theorem of the nine theories carries only the `DISK_THM` tag of a loaded theory, and none of
them declares an axiom.

## Sources

P is the RISC-V Instruction Set Manual, Volume II: Privileged Architecture, version 20260120; U
is Volume I. The PMP rules are those of P §3.7 (p.70-74): the entry configuration and address
registers (§3.7.1, Figures 31-34, Table 24), address matching (§3.7.1.1), locking (§3.7.1.2)
and priority: "the lowest-numbered PMP entry that matches any byte of an access determines
whether that access succeeds or fails ... the matching PMP entry must match all bytes of an
access, or the access fails ... if no PMP entry matches an S-mode or U-mode access, but at
least one PMP entry is implemented, the access fails" (§3.7.1.3 p.73). The model implements
them in `pmpCheck`, `pmpEntryCheck`, `pmpRegion` and `pmpPermits`
(`../doc/design-privileged.md` chapter 5, [D47]-[D62]), checks explicit data accesses with
the effective privilege (P §3.1.6.4 p.35, [D22]) and fetches with the current one, parcel by
parcel ([D59]); address translation is `translateAddr` (`../doc/design-smode.md` chapter 3).

Notation: `s : riscv_state`; the hart is `s.procID`; memory is `s.MEM8 : word64 -> word8`;
`pmpCheck (a, n, kind, p) s` is the model's check of an `n`-byte access at `a` of kind
`PMP_Read`, `PMP_Write`, `PMP_ReadWrite` (AMOs) or `PMP_Execute` by privilege `p`; so
`pmpCheck (x, 1, PMP_Write, User) s` says that the PMP configuration of `s` lets U-mode write
the byte `x`.

## The theorems (`riscv_isolationTheory`)

The U-mode hypotheses are bundled as `U_bare s`: the hart is in U-mode
(`curPrivilege () s = User`), its explicit accesses are made with U-mode privilege
(`effectivePrivilege () s = User`) and translation is off (`satp_bare s`). `U_bare_intro`
gives it from the register-level conditions that HolBA's contracts state: `c_privilege = 0`,
`mstatus.MPRV = 0`, `satp.MODE = 0`.

### (a) Write frame

- `Next_writes`: every byte that a step changes is one of the `n` bytes at `va` of the data
  access of the instruction that the step runs (`step_inst s`), which is a store, SC, AMO or
  FP store (kind `PMP_Write`, or `PMP_ReadWrite` for an AMO), is naturally aligned, and passed
  `pmpCheck (va, n, kind, effectivePrivilege () s) s` in the configuration of `s`. Hypothesis:
  translation off (`effectivePrivilege () s = Machine \/ satp_bare s`).
- `Next_U_writes`: the same in U-mode with Bare `satp`, the check being for `User`.
- `Next_U_writes_byte`: so every byte that a U-mode step changes satisfies
  `pmpCheck (x, 1, PMP_Write, User) s`: the PMP lets U-mode write it.
- `Next_U_writes_words`: the same as a function of the words `pmpcfg0`, `pmpcfg2`,
  `pmpaddr0`-`pmpaddr15` (`pmp_check`, below).
- `Next_writes_pa`: with no hypothesis on the privilege or `satp`: every changed byte is a
  byte of the physical address `pa` that `dataAddr` gave for the access, and that physical
  access passed the PMP check for the effective privilege. (The model never writes page-table
  entries.)
- `Next_U_secret_unchanged`: a U-mode step leaves unchanged every byte that U-mode may not
  write.

### (b) Fetch

`fetch_bytes s x` (stage 1) holds for the bytes of the parcels at the pc and at pc + 2 that
`fetchAddr` approved; `Fetch_reads` (stage 1) shows that these are the only bytes that the
fetch reads, and `Next_reads` below that the step depends on no other bytes beyond the data
and the CLINT.

- `Next_U_fetch`: in U-mode with Bare `satp`, every byte of a fetched parcel satisfies
  `pmpCheck (x, 1, PMP_Execute, User) s`. `Next_U_fetch_words` is the word-level form, and
  `fetch_bytes_pmp` the physical form with no hypothesis: each such byte belongs to a 2-byte
  parcel at a physical address that passed the execute check for the current privilege.
- `Next_fetch_fault`, `Next_U_fetch_fault`: when the parcel at the pc, or the second parcel of
  a 32-bit instruction, is not executable (`fetch_fault s a`, with `a` its address), and the
  step takes no interrupt, the step is exactly the trap entry of an instruction access fault
  (code 1, P Table 16 p.50) with the parcel's address as the trap value (P §3.1.16 p.52,
  [D59]), to M or, if `medeleg` delegates it, to S (`excDest (1w, User) s`, P §3.1.8), from
  the state `fetch_fault_state s a`; memory is unchanged.

### (c) Read dependence

`step_reads s x` is the set of bytes a step reads: the CLINT bytes of the hart (`mtime`,
`mtimecmp`, `msip`, which the interrupt check and the `time` CSR read), the fetched parcels
when no interrupt is taken, and the data that the instruction reads (loads, LR, AMOs, FLW,
FLD).

- `Next_reads`: two states that are equal except on a set `D` of bytes (`same_except D`) that
  contains no byte of `step_reads s1` take steps whose results are equal except on `D`.
  Hypothesis: translation off for the fetch and for the data access.
- `step_reads_U`: in U-mode with Bare `satp`, every byte the step reads is a CLINT byte or
  one that U-mode may execute or read.
- `Next_U_reads`: so two U-mode states that differ only on bytes that U-mode may neither read
  nor execute, and that are not CLINT bytes, take steps that differ only there. The PMP
  configuration, being outside memory, is the same in both.
- `Next_U_reads_unchanged`: with a legal PMP configuration (`pmp_legal`: no entry has W = 1
  and R = 0, [D49]) those bytes are not writable either, so both steps leave them unchanged.

### (d) Companion frames

- `Next_U_frame`: a U-mode step from a state between steps (`c_NextFetch = NONE`) keeps
  `procID`, `totalCore`, the M-level CSRs that no trap entry writes (`mcsr_same`: `misa`,
  `mhartid`, `medeleg`, `mideleg`, `mie`, `mtvec`, `mcounteren`, `menvcfg`,
  `mcountinhibit`, `mscratch`, `mip`, `pmpcfg0`, `pmpcfg2`, `pmpaddr0`-`pmpaddr15`, and
  `mstatus` but for its trap-entry fields MIE, MPIE, MPP, SIE, SPIE, SPP and FS) and the
  S-level ones (`scsr_same`: `satp`, `stvec`, `scounteren`, `senvcfg`, `sscratch`);
  `mstatus.FS` is unchanged or becomes Dirty (3); while FS is Off it stays Off and the FP
  registers and `fcsr` are unchanged (P §3.1.6.7 p.38); the load reservation changes only if
  the instruction is LR or SC; and `c_NextFetch` is `NONE` again.
- `Next_U_trap`: either the privilege and the trap CSRs (`mepc`, `mcause`, `mtval`, `sepc`,
  `scause`, `stval`, and the trap-entry fields of `mstatus`) are unchanged, or the step is a
  trap entry (`takeTrap`) to M or S, as `mideleg` (an interrupt, from `checkInterrupts`) or
  `medeleg` (an exception, `excDest`) delegate (P §3.1.8 p.42-43), from a state with the CSRs,
  privilege, pc, memory and hart of `s`; the trap changes no memory. An instruction that traps
  changed no M-level CSR and no memory before signalling ("PMP violations are always trapped
  precisely", P §3.7 p.70); the theorem says nothing about the GPRs, FPRs, `fcsr` or the
  reservation of a trapping instruction.
- `Next_U_shape`: the four forms of a U-mode step: the entry of an interrupt, the next
  instruction, a branch, or the trap entry of an exception raised by the instruction.
- `Run_U` (with one lemma `dfn'<I>_U` per instruction definition, 161 of them): every
  instruction run in U-mode keeps the privilege, the pc and the S-level CSRs, keeps the
  M-level CSRs but for FS, never schedules MRET or SRET (illegal in U-mode, P §3.3.2 p.61),
  and when it traps has changed no M-level CSR and no memory. `checkCSROp_User`: U-mode may access only `fflags`, `frm`, `fcsr`
  (while FS is not Off) and read `cycle`, `time`, `instret` (P §2.1 p.13).
- `Next_U_stays`: a U-mode step that does not change the privilege leaves `U_bare`,
  `c_NextFetch = NONE` and the PMP configuration as they were, so the theorems apply again to
  the next step with the same configuration.

### Word-level PMP conditions (`riscv_pmpTheory`)

`pmp_check (cfg0, cfg2, addr) (a, n, kind, p)` is the model's check written over the words
`pmpcfg0`, `pmpcfg2` and `addr i` = `pmpaddr<i>` alone (entry `i` is byte `i mod 8` of
`pmpcfg0` or `pmpcfg2`, Figure 31; L, A, X, W, R are bits 7, 4:3, 2, 1, 0, Figure 34).

- `pmpCheck_words`, `pmpCheck_MCSR`: `pmpCheck acc s` equals `pmp_check` of the hart's 18 PMP
  CSR words, with `\i. pmpaddr i s` or `pmpaddr_of (s.c_MCSR s.procID)`; so a contract that
  fixes the words can decide every side condition above by `EVAL` or bit-blasting
  (`ex_pmp_check` does). `pmpCheck_eq`: equal words give equal checks.
- `pmpCheck_first`, `pmpCheck_byte_first`: the check is the verdict of the first entry that
  has one; for one byte, the lowest-numbered entry that matches it decides, M-mode passing an
  unlocked entry, and an unmatched byte is allowed only to M-mode (§3.7.1.3).
- `pmpCheck_byte`: an aligned 1, 2, 4 or 8-byte access that the check allows is allowed for
  each of its bytes, at any privilege. `pmpCheck_sub`, `pmpCheck_kind`: sub-accesses and
  weaker kinds. `pmpCheck_RW`: an AMO's check implies a read and a write check.
- `pmp_legal`, `pmp_legal_bits` (the bit form `cfg >>> 1 && ~cfg && 0x0101010101010101w =
  0w`), `pmp_legal_write_read` (a writable byte is readable), `legalize_pmpcfg_legal` (every
  value `legalize_pmpcfg` computes is legal if the old one was; that `writeCSR` of `pmpcfg0`
  and `pmpcfg2` stores `legalize_pmpcfg (v, old)` is by reading `writeCSR`, and the legality
  of the reset value 0 follows from `pmp_legal_bits`; neither is stated as a theorem).

### The entry and the region of a byte that U-mode may access (`riscv_pmpTheory`)

For a 1-byte access by U-mode the check is the permission of the lowest-numbered entry that
matches the byte, and some entry must match (§3.7.1.3 p.73). An entry is OFF or NAPOT when the
two bits of its A field are equal (Table 23 p.72); a NAPOT entry matches the region that its
address word encodes (Table 24 p.72).

- `pmpCheck_User_entry`: if `pmpCheck (x, 1, kind, User) s`, then there are `i < 16` and
  `lo`, `hi` with `pmpRegion (n2w i) s = SOME (lo, hi)`, `lo <=+ x`, `x <+ hi`, the entry's
  configuration allows the kind (`pmpPermits (pmpcfg_ent (n2w i) s, kind)`), and no entry
  `j < i` matches `x` (`pmp_match`). No hypothesis on the configuration: it is
  `pmpCheck_byte_first` at User privilege, where an unmatched byte is refused and the lock bit
  plays no part.
- `pmpRegion_pmpcfg2_off`: with `pmpcfg2 = 0`, entries 8-15 are OFF (`pmpRegion` gives
  `NONE`), since they are configured by the bytes of `pmpcfg2`. `pmpCheck_User_low`: so with
  `pmpcfg2 = 0` the entry of `pmpCheck_User_entry` is one of 0-7.
- `pmp_match_w`, `pmp_match_words`, `pmp_entry_User_byte`, `pmp_check_User_byte`: the same
  over the words. `pmp_match_w (cfg0, cfg2, addr) i x` holds when `pmp_region (cfg0, cfg2,
  addr) i = SOME (lo, hi)` with `lo <=+ x` and `x <+ hi`, and `pmp_match_words` relates it to
  `pmp_match` as `pmpCheck_words` relates the checks. For a 1-byte access by U-mode an entry's
  verdict is `NONE` if it does not match the byte and the permission of its configuration byte
  for the kind (`pmp_perm`) if it does (`pmp_entry_User_byte`), so `pmp_check w (x, 1, kind,
  User)` holds iff some entry `i < 16` matches `x`, no lower entry does, and `pmp_perm` of its
  byte allows the kind (`pmp_check_User_byte`, an equivalence).
- `napot_region`, `pmp_region_off_napot`, `off_or_napot_bytes`: `napot_region y` is the pair
  `(lo, hi)` of the region that a NAPOT entry with address word `y` matches, as `pmp_region`
  computes it; an entry whose A field is 0 has no region, and one whose A field is 3 has
  `napot_region (addr i)` (`pmp_region_off_napot`); and the bit condition
  `(cfg >>> 1 ?? cfg) && 0x0808080808080808w = 0w` on `pmpcfg0` and on `pmpcfg2`, which says
  that bits 4 and 3 of every byte are equal (the step library's `pmp_off_or_napot`, H4), makes
  the A field of every entry 0 or 3 (`off_or_napot_bytes`).
- `pmp_check_User_napot`: if both configuration words satisfy that bit condition and
  `pmp_check (cfg0, cfg2, addr) (x, 1, kind, User)` holds, then there is an entry `i < 16` whose
  A field is 3 (NAPOT), whose configuration byte allows the kind (`pmp_perm`), with
  `FST (napot_region (addr (n2w i))) <=+ x` and `x <+ SND (napot_region (addr (n2w i)))`, and no
  entry `j < i` matches `x` (`pmp_match_w`). `pmpCheck_User_napot` is the same for a state, over
  the words as `pmpCheck_words` reads them: `pmpcfg0` and `pmpcfg2` of the hart, and
  `pmpaddr (n2w i) s` for `addr (n2w i)`. The bit condition is needed because a TOR entry's
  region also depends on the address word below it and an NA4 region is not `napot_region`.

### The sanity check (`riscv_isolation_exampleTheory`)

On one PMP region (entry 0 NAPOT, R = W = X = 1, 4 KiB at 0x80000000, entries 1-15 OFF:
`ex_pmp`): `ex_pmp_check` evaluates the word-level check (allowed exactly inside the region);
`ex_writes` is (a), every byte a U-mode step changes is inside; `ex_reads` is (c). For a state
with `sd x6, 0(x5)` (0x0062B023, `ex_sd_decode`) at a 4-aligned pc inside the region
(`ex_state`), `ex_store_inside`: if x5 is an aligned address inside the region the step
writes the 8 bytes of x6 there and changes no other byte and not the privilege;
`ex_store_outside`: otherwise the step is the trap entry of a store access fault (code 7) with
x5 as the trap value, and memory is unchanged. `Fetch_word` is the fetch of a 32-bit
instruction from two executable parcels.

## Trap entry from U-mode (`riscv_trapTheory`)

What an M-mode kernel that takes system calls by `ecall` needs of the step that enters it, and
of the steps that take no interrupt.

- `Next_U_ecall`: let `s` be in U-mode (`curPrivilege () s = User`), let its step run ECALL
  (`step_inst s = SOME (System ECALL)`: no interrupt is taken and the fetched parcels decode
  to ECALL), and let bit 8 of `medeleg` be clear. Then the step is the trap entry of the
  environment call from U-mode into M-mode (P §3.3.1 p.60-61, cause 8 of Table 16 p.50):
  `procID` is unchanged; the privilege of the hart becomes 3; its pc becomes
  `trapVector (mtvec, F, 8w)`; `mcause` becomes `<| EC := 8w; Int := F |>`, `mepc` the pc of
  the `ecall` (`PC s`) and `mtval` 0 (P §3.1.14-3.1.16 p.48-53); `mstatus` becomes the old
  value with MIE cleared, MPIE set to the old MIE and MPP set to 0, U (P §3.1.6.1 p.32);
  every other field of the hart's M-level CSRs is unchanged (the record of `Next s` with
  `mcause`, `mepc`, `mtval` and `mstatus` put back is that of `s`); the S-level CSRs, the GPRs
  and memory are unchanged (as whole functions, all harts); `c_NextFetch` of the hart is
  `NONE`; and the `exception` field is unchanged.
  Hypotheses: U-mode, because ECALL raises the environment call of the current privilege and
  MPP records that privilege (0 also when `c_privilege` holds the reserved 2, which reads as
  U); `step_inst`, which is what says that the step runs ECALL rather than an interrupt or a
  fetch fault; bit 8 of `medeleg` clear, because a delegated environment call goes to S-mode
  and writes `scause`, `sepc` and `stval` instead (P §3.1.8 p.42). There is no hypothesis on
  `c_NextFetch` (ECALL sets it to the trap, which the step takes and clears), on `satp` or on
  `MPRV`.
- `checkInterrupts_U_MTIP`: if `curPrivilege () s = User`, MTIE (bit 7 of `reg'mie mie`) is
  set and `checkInterrupts () s = NONE`, then `~(mtimecmp s.procID s <=+ mtime () s)`: the
  timer interrupt, whose pending bit `read_mip` computes from the CLINT (P §3.2.1 p.59, [D67]),
  is not pending. There is no hypothesis on `mideleg`: in U-mode an interrupt that is pending
  and enabled in `mie` is taken into M when `mideleg` does not delegate it and into S when it
  does (P §3.1.9 p.43, §12.1.3 p.117), so either way one would be taken.
- `Next_U_stays_no_interrupt`: if `s.c_privilege s.procID = 0w` and the step leaves the
  privilege of the hart unchanged, then `checkInterrupts () s = NONE`: an interrupt is taken
  into M or S (`checkInterrupts_dest`, `takeTrap_fields`), which changes the privilege to 3 or
  1.
- `step_inst_SOME`: a step that runs an instruction (`step_inst s = SOME i`) took no interrupt.
- `Fetch_exception`, `exec_state_exception`: the spec's `Fetch`, and so the state in which the
  instruction runs, leave the `exception` field unchanged (a failed fetch returns `F_Error`
  rather than raising an exception).
- `curPrivilege_User`: `curPrivilege () s = User` iff the hart's `c_privilege` is 0 or the
  reserved 2.
- `reg'mcause_8`: the word of an `mcause` value is 8 iff its exception code is 8 and its
  interrupt bit is clear (P §3.1.15 Figure 22 p.49).
- `trapVector_direct`: when bits 1:0 of `mtvec` are 0 (Direct mode) the vector of every trap is
  `mtvec` itself (P §3.1.7 Table 15 p.41). `trapVector_exception`: the vector of an exception
  is `mtvec && ~3w` in both modes.

The build of `riscv_trapTheory` checks that `riscv_stepTheory` is not an ancestor of
`riscv_isolationTheory`, and so of the theories below it (`DESIGN.md` I11); `riscv_trapTheory`
has it as an ancestor, opened qualified only, for `takeTrap_Machine` and `read_mip_eval`.

### The sanity check of the trap theorems (`riscv_trap_exampleTheory`)

On the configuration `ex_pmp` of `riscv_isolation_exampleTheory`, `ex_ecall_state s` is a
U-mode state with Bare `satp`, only the timer interrupt enabled (`reg'mie mie = 0x80w`) and not
pending, `medeleg = 0`, `mtvec` in Direct mode and `ecall` (0x00000073, `ex_ecall_decode`) at
a 4-aligned pc inside the region. `ex_timer_only`: with only MTIE enabled, a U-mode state takes
no interrupt iff the timer interrupt is not pending (one direction is `checkInterrupts_U_MTIP`).
`ex_ecall_step_inst`: the step runs ECALL. `ex_ecall`: it enters M-mode at `mtvec` with
`mcause` 8 (`reg'mcause_8`), `mepc` the pc, MPP U and MIE clear, and changes neither the GPRs,
nor memory, nor the PMP configuration. `ex_ecall_state_witness`: a concrete state
(`ex_ecall_witness`: hart 0 at 0x80000000 with `ecall` there, `mtimecmp` all ones and `mtime`
0 in the CLINT, `mtvec` = 0x80002000, the other fields left unspecified, `ARB`) satisfies
`ex_ecall_state`, so the hypotheses of `Next_U_ecall` can hold together;
`ex_ecall_witness_trap`: its step runs ECALL and enters M-mode at 0x80002000 with `mepc` =
0x80000000 and `mcause` 8.

## `Next` and the step library's `NextRISCV` (`riscv_refineTheory`)

The step library (`../step/riscv_stepScript.sml`) proves M-mode step theorems
`hyps |- NextRISCV s = SOME s'`, and HolBA's lifter and backlifter reason with `NextRISCV`
(`riscv_bmr.bmr_step_fun`). `NextRISCV` runs the instruction at the pc as `Next` does, but takes
no interrupt, fetches without the logging of the spec (`setupDelta`), returns `NONE` when the
model's `exception` field is set (its `Fetch` sets it where the spec's returns `F_Error`, at a
misaligned pc or a fetch fault) and for SRET, and counts nothing.
This theory proves that the two steps agree on every field of the state but six.

- `ghost_reset s` is `s` with the ghost fields `log`, `c_update`, `exception`, `c_cycles`,
  `c_instret` and `c_minstret_written` set to `[]`, `K ARB`, `NoException`, `K 0w`, `K 0w` and
  `K F`; `ghost_eq s t` is `ghost_reset s = ghost_reset t`: `s` and `t` agree on every other
  field (`ghost_eq_fields`; an update of a ghost field gives a ghost-equal state,
  `ghost_eq_ghost_fupd`; `ghost_eq_refl`, `ghost_eq_sym`, `ghost_eq_trans`, `ghost_eq_reset`,
  `ghost_reset_idem`). The build computes the six from the model and stops if they change: the
  fields that `Next` updates outside the instruction (in its own definition, `clear_logs` and
  `incrInstret`), those that the spec's `Fetch` updates and the step library's does not, and
  those that `NextRISCV` reads (the exception, for its `NONE`).
- `counter_csr c`: `c` is `mcycle`, `minstret`, `cycle` or `instret` (0xB00, 0xB02, 0xC00,
  0xC02; P §3.1.10 p.46, §3.1.11 p.47); the build checks that these are exactly the cases of
  `CSRMap` that read `c_cycles` or `c_instret`. `reads_counter i`: `i` is one of the six CSR
  instructions (CSRRW, CSRRS, CSRRC and their immediate forms) on a counter CSR, whatever its
  destination register.

### A ghost lemma for every function

The build computes, as `riscv_framesTheory` does for its frames, which of the 253 state
functions reachable from `Next` mention a ghost field, directly or through a callee, and stops
if they are not the expected 66, or if the definitions that mention one themselves are not
`clear_logs` (`log`), `Delta` and `write'Delta` (`c_update`, read and written only by `Fetch`,
`writeCSR`, `writeFPRS` and `writeFPRD`), `raise'exception` (`exception`), `CSRMap` and
`write'CSRMap` (the counters), `incrInstret` and `Next`.

- `<f>_ghost` for each of the other 187 (generated): `f x (ghost_reset s) = ghost_reset (f x s)`
  for a state transformer, `(FST (f x s), ghost_reset (SND (f x s)))` for a function that
  returns a value and a state, `f x s` for one that returns a value. So `f` neither reads nor
  writes a ghost field.
- For the 66, ghost-equal states give ghost-equal states and equal values, or the function
  changes only ghost fields:
  - `write'Delta_ghost`, `clear_logs_ghost`, `incrInstret_ghost`: `ghost_eq (f x s) s`;
    `raise'exception_ghost`: it returns `ARB` and changes only the exception; `CSRMap_state`: a
    CSR read changes at most the exception (for a CSR number that `CSRMap` does not list);
  - `CSRMap_ghost`, `CSR_ghost`: on ghost-equal states a CSR read gives ghost-equal states,
    and, for a CSR other than a counter (`~counter_csr c`), equal values;
  - `write'CSRMap_ghost`, `write'CSR_ghost`, `writeCSR_ghost`: a CSR write, of a counter too
    (which writes only ghost fields); `writeCSR_write'CSRMap`: `writeCSR`, which logs the
    value it reads back in `c_update`, is `write'CSRMap` up to the ghost fields;
  - `accessCSR_ghost` and `dfn'CSRRW_ghost`, `dfn'CSRRS_ghost`, `dfn'CSRRC_ghost`,
    `dfn'CSRRWI_ghost`, `dfn'CSRRSI_ghost`, `dfn'CSRRCI_ghost`: a CSR instruction on a CSR other
    than a counter;
  - `writeFPRS_ghost`, `writeFPRD_ghost`, and `<f>_ghost` (generated) for the 42 F and D
    instructions that write an FPR, which log the value in `c_update`;
  - `Fetch_ghost`: the spec's fetch; `takeTrap_ghost` (generated): the trap entry, whose ghost
    access is the exception of a trap to U-mode;
  - `Run_ghost`: `~reads_counter i /\ ghost_eq s t ==> ghost_eq (Run i s) (Run i t)`;
  - `Next_ghost`: `ghost_eq s t` and no instruction that the step runs (`step_inst s`) reads a
    counter give `ghost_eq (Next s) (Next t)`.

  `Delta`, whose value is the ghost field `c_update`, has no lemma (its four callers have), nor
  has `fetchAndExecute`, which `Next_ghost` covers; the build checks that every other function
  reachable from `Next` has one.
- `Run_exception`: an instruction keeps an exception that has been raised
  (`s.exception <> NoException ==> (Run i s).exception = s.exception`): `raise'exception` sets
  the field only while it is `NoException`, and nothing else writes it.

### The step

- `Fetch_step_spec`: where the step library's `Fetch` returns `(w, s1)` with no exception before
  or after, the spec's `Fetch` returns `F_Result w` and `s1` but for `c_update`.
  `Fetch_spec_step`: whatever the fetch does, the states of the two fetches are ghost-equal (the
  spec's returns `F_Error` where the step library's raises an exception).
  `Fetch_step_exception`, `NextRISCV_exception`: a step of `NextRISCV` starts with no exception
  and its fetch raises none (by `Run_exception`), so it never follows a failed fetch.
- `cycle_step_ghost`, `next_pre_ghost`, `exec_state_ghost`: the parts of `Next` before and after
  the instruction (as `Next_split` of `riscv_isolationTheory` splits it) change only ghost
  fields; `next_post_ghost`: the dispatch on `NextFetch` after the instruction (with or without
  counting it) is a congruence for `ghost_eq`; `NextRISCV_next_post`: a step of `NextRISCV` is,
  up to the ghost fields, that dispatch after `Run` of the instruction that its fetch read.
- `Next_NextRISCV_ghost`:

      !s t t'. ghost_eq s t /\ (checkInterrupts () t = NONE) /\
               (!w t1. (riscv_step$Fetch t = (w, t1)) ==>
                       ~reads_counter (DecodeAny (haveRVC () t) w)) /\
               (NextRISCV t = SOME t') ==>
               ghost_eq (Next s) t'

  If `t` takes no interrupt, the instruction that the step library's fetch reads at `t` reads no
  counter CSR, and `NextRISCV t = SOME t'`, then the spec's step from any state ghost-equal to
  `t` is ghost-equal to `t'`. Applied at each step, it relates a run of `NextRISCV` whose states
  take no interrupt and whose instructions read no counter to the run of `Next` from a
  ghost-equal state (by induction on the run, which is not stated here). Nothing is said of the
  ghost fields of `Next s`.

### The sanity check of the refinement (`riscv_refine_exampleTheory`)

For each of `csrw pmpcfg0, t0` (0x3A029073), `sd x6, 0(x5)` (0x0062B023), `c.jr ra` (0x8082),
`beq x0, x0, 8` (0x00000463) and `mret` (0x30200073), the build takes the step library's
theorem `hyps |- NextRISCV s = SOME s'` and proves `<name>_refine`:
`!s. hyps ==> !s0. ghost_eq s0 s ==> ghost_eq (Next s0) s'`. The no-interrupt hypothesis
follows from privilege M and MIE clear, which every step theorem assumes (H1, H6,
`checkInterrupts_Machine`), and the fetch hypothesis from the instruction bytes in `hyps`
(`Fetch32`, `Fetch16` of `riscv_stepTheory`) and the decoding of the instruction; the build
checks that no hypothesis is added. `cycle_read_refused`: `csrr a0, cycle` (0xC0002573) reads a
counter CSR, and the build checks that the instance fails for its step theorem.

## Hypotheses, and why each is needed

| Hypothesis | Used by | Why |
|---|---|---|
| `effectivePrivilege () s = User` (from `mstatus.MPRV = 0` in U-mode, `U_bare_intro`) | (a) U-forms, (c) | explicit loads and stores are checked with the effective privilege (P §3.1.6.4 p.35, [D22]); with MPRV = 1 and MPP = M a U-mode store would be checked as M and pass every unlocked entry. An xRET that leaves M clears MPRV, so it is 0 in a reachable U-mode state. |
| `curPrivilege () s = User` (from `c_privilege = 0`) | (b), (c), (d), `Next_U_ecall`, `checkInterrupts_U_MTIP` | fetches are checked with the current privilege (P §3.7.1 p.72); it is what makes CSR access, xRET, WFI and SFENCE.VMA illegal and decides which interrupts are enabled; ECALL raises the environment call of the current privilege, and MPP records it. It is weaker than `c_privilege = 0`: the reserved encoding 2 also reads as U. |
| `satp_bare s` (from `satp.MODE = 0`) | (a), (b), (c) in their U and byte forms | translation is out of scope: the byte forms need the physical address to be the virtual one, and (c) would have to add the page-table entries to the bytes read. Only Sv39, Sv48 and Sv57 turn translation on (P §12.1.11 Table 40 p.126), so this is weaker than MODE = 0. The physical forms `Next_writes_pa` and `fetch_bytes_pmp` and the frames (d) need no hypothesis on `satp`. |
| `checkInterrupts () s = NONE` | `Next_U_fetch_fault` | a step that takes an interrupt fetches nothing (P §3.1.14 p.49, [D38]). |
| `D` has no CLINT byte | `Next_U_reads` | the interrupt check reads `mtime`, `mtimecmp` (MTIP, P §3.2.1 p.59) and `msip` (P §3.1.9 p.44) from memory without a PMP check ([D67]), and so does a read of the `time` CSR: two states that differ there can differ in whether a timer interrupt is taken. This is the platform timer, not a PMP leak. |
| `s.c_NextFetch s.procID = NONE` | (d) | it holds between steps (`Next` resets it in every branch, and `Next_U_frame` proves it again for `Next s`); a stale `SOME Mret` would make `Next` perform an MRET after a U-mode instruction. |
| `pmp_legal` | `Next_U_reads_unchanged` | with an entry W = 1, R = 0 a byte could be writable but not readable; `legalize_pmpcfg_byte` never stores one ([D49], `legalize_pmpcfg_legal`). |
| privilege unchanged | `Next_U_stays` | it is what tells a step that does not trap. |
| `c_privilege = 0` and the privilege unchanged | `Next_U_stays_no_interrupt` | an interrupt changes the privilege only because it is taken from U-mode into M or S; from S-mode an interrupt that `mideleg` delegates is taken into S and keeps the privilege. |
| `step_inst s = SOME (System ECALL)` | `Next_U_ecall` | it says that the step takes no interrupt and that the fetched instruction is ECALL; an interrupt, a fetch fault or another instruction is another trap or none. |
| bit 8 of `medeleg` clear | `Next_U_ecall` | an environment call from U-mode that `medeleg` delegates goes to S-mode (P §3.1.8 p.42) and writes `scause`, `sepc`, `stval` and the S-level fields of `mstatus` instead. |
| MTIE set (bit 7 of `reg'mie mie`) | `checkInterrupts_U_MTIP` | with the timer interrupt disabled a pending timer causes no trap, and taking no interrupt says nothing of MTIP. |
| every entry OFF or NAPOT (`(cfg >>> 1 ?? cfg) && 0x0808080808080808w = 0w` for `pmpcfg0` and `pmpcfg2`) | `pmp_check_User_napot`, `pmpCheck_User_napot` | a TOR entry's region also depends on the address word below it, and an NA4 region is not `napot_region`; with OFF and NAPOT entries only, the region of every matching entry is the NAPOT region of its own address word. |
| `pmpcfg2 = 0` | `pmpRegion_pmpcfg2_off`, `pmpCheck_User_low` | entries 8-15 are configured by `pmpcfg2`, so they are then OFF. |
| `ghost_eq s t` | `Next_NextRISCV_ghost`, `Next_ghost`, `Run_ghost` and the relational ghost lemmas | it is what is preserved: the states agree on every field but the six ghost fields, which `NextRISCV` does not maintain (it never clears the log, logs no fetch and counts nothing). |
| `checkInterrupts () t = NONE` | `Next_NextRISCV_ghost` | `NextRISCV` takes no interrupt; `Next` takes one that is pending, enabled and allowed in the current mode (P §3.1.9 p.43-45) instead of running the instruction. In M-mode MIE clear gives it (`checkInterrupts_Machine`). |
| the fetched instruction reads no counter CSR (`~reads_counter`) | `Next_NextRISCV_ghost`, `Next_ghost`, `Run_ghost` | `Next` counts cycles and retired instructions and `NextRISCV` does not, so their `c_cycles` and `c_instret` differ after a step, and a read of `mcycle`, `minstret`, `cycle` or `instret` would put different values in a register. |
| `~counter_csr c` | `CSRMap_ghost` (the value), `CSR_ghost`, `accessCSR_ghost`, `dfn'CSRR*_ghost` | the same, for one CSR access. |
| `NextRISCV t = SOME t'` | `Next_NextRISCV_ghost` | `NextRISCV` is `NONE` after a failed fetch, an exception raised by the instruction, and for SRET, where the two steps are not related. |

## Limits

- Translated U-mode (Sv39/Sv48/Sv57) is covered only by the physical forms of (a) and (b) and
  by (d); (c) and the byte forms assume Bare `satp`.
- The CLINT is ordinary memory in this model and is read without a PMP check (above).
- The theorems are about the hart `s.procID`; for the other harts of a multi-hart state they
  say only what the whole-function equalities say (of `c_privilege` in `Next_U_trap`, of
  `c_fpr`, `c_UCSR` and `c_ReserveLoad` in `Next_U_frame`, and of memory).
- The exact trap state is proved only for ECALL from U-mode into M-mode (`Next_U_ecall`); an
  ECALL that `medeleg` delegates, and every other trap from U-mode, are covered by
  `Next_U_trap` only. `Next_U_ecall` says nothing of `c_fpr`, `c_UCSR`, `c_ReserveLoad` or the
  counters.
- The region of a U-mode byte is given only for configurations whose entries are all OFF or
  NAPOT (`pmp_check_User_napot`); with TOR or NA4 entries there is only the first matching entry
  and its `pmpRegion` (`pmpCheck_User_entry`).
- `Next_NextRISCV_ghost` relates one step, from a state that takes no interrupt, for an
  instruction that reads no counter CSR and for which `NextRISCV` is not `NONE`; it says nothing
  of the ghost fields after the step (`Next` has counted the cycle and the instruction,
  `NextRISCV` has not).

## Stage 1: `riscv_footprintTheory`

**Which functions touch memory.** Of the 253 functions reachable from `Next` that involve the
state, the build computes the 67 whose definitions mention memory, directly or through a
callee, and fails if they are not the expected list (`DESIGN.md` §3.2). For each of the other
186, `f_MEM8` proves that `f` commutes with replacing the memory, so it neither reads nor
writes it; `f_MEM8_frame` that it leaves memory unchanged, and `f_procID` that it leaves
`procID` unchanged (for the 153 that return a state).

**Memory primitives, at every alignment.** `rawReadData_bytes`, `rawWriteData_bytes`,
`rawWriteData_eq`, `rawWriteData_MEM8`, `rawWriteData_frame`, `rawReadData_agree_1/2/4/8`,
`write'MEM_bytes`, `rawReadInst_eq`.

**The PMP check of an access.** `dataAddr_pmpCheck`, `fetchAddr_pmpCheck` (any translation);
`translateAddr_off`, `dataAddr_off`, `fetchAddr_off`, `dataAddr_off_MEM8`,
`fetchAddr_off_MEM8` (translation off); `align_tests`.

**The CLINT.** `checkInterrupts_CLINT`, `read_mip_CLINT`, `CSRMap_CLINT`, `accessCSR_CLINT`,
`writeCSR_CLINT`, `dfn'WFI_CLINT`: these depend on memory only through the CLINT bytes of the
hart (`clint_byte`).

**Every instruction that accesses memory.** The 37 instruction definitions that call
`dataAddr` are listed in `mem_access` with their access. `<I>_writes`, `<I>_MEM8_frame`,
`<I>_reads` for each; for the CSR instructions and WFI, `<I>_MEM8_frame` and `<I>_reads` with
the CLINT bytes. `Run_writes`, `Run_reads`, `Run_MEM8_frame` for every instruction at once.

**Fetch.** `Fetch_MEM8_frame`, `Fetch_reads`, `fetch_bytes_off`, `fetchAddr_Skip`,
`Fetch_MEM8`.

## Field frames: `riscv_framesTheory`

The build computes, for each of the 253 state functions reachable from `Next`, the record
fields that its definition updates, directly or through a callee, and checks that only the
expected functions update the privilege, the pc, the S-level CSRs, the load reservation,
`procID` and `totalCore`. For every function other than `Next`, `fetchAndExecute` and `Run`
it proves `<f>_frame`: the fields among `procID`, `totalCore`, `c_privilege`, `c_PC`,
`c_SCSR`, `c_MCSR`, `c_fpr`, `c_UCSR`, `c_ReserveLoad`, `c_NextFetch`, `c_gpr` and `MEM8`
that it does not update are unchanged (205 theorems). `<f>_log` and `<f>_minstret` (26 each)
show that `Fetch`, `checkInterrupts` and the functions they call commute with the reset of
`log` and `c_minstret_written` with which `Next` starts.
